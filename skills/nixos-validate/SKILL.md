# nixos-validate（防御仮説を nixosTest で確かめる）

引数は `<対象> <仮説>` である。対象は `t14-pam`、`t14-luks`、`tegata` のような、ホストと部位が分かる短い名前とする。仮説は「〜できる」の形の一文とする。

対象は、たいらが所有する端末の設定のみである。他人のホストや外部サービスを対象にしない。弱点を突く操作は VM の中だけで行い、実機には作用させない。

## 手順

補助スクリプトは本スキルのディレクトリの `run.sh` である（以下 `run.sh` と書く。実体は `~/.claude/skills/nixos-validate/run.sh`）。

1. **既存の試験を探す。** `run.sh find <対象> [語...]` を実行する。ファイル名または冒頭の仮説行に、指定した語をすべて含む試験が列挙される
2. **流用か新規かを決める。** 仮説が同じ試験があれば、そのまま使う。対象は同じで仮説が違う場合は、ノードの構成を写す元として読み、新しい試験を作る
3. **新規の場合は雛形を生成する。** `run.sh new [--host <名前>] <対象> <短縮名> <仮説>` を実行し、出力されたファイルに検証手順を記述する。`--host` は設定を参照する `nixosConfigurations` の属性名で、既定は `t14` である
4. **実行する。** `run.sh run <試験ファイル>` を実行する。初回は VM の部品を取得するため数分かかる
5. **報告する。** 判定、判定行の根拠、ログのパス、再現コマンド、VM と実機の差を伝える

## 試験の規約

- 試験は「防御が有効な状態」を表明する。弱点が成立するときに失敗させる
- 判定は雛形の `verdict(防御が有効か, 根拠)` で記録する。`run.sh` はこの判定行と `nix build` の終了コードを突き合わせる

| 終了コード | 意味 |
|---|---|
| 0 | 防御は有効（試験が成功し、判定行が DEFENDED） |
| 1 | 弱点が成立（判定行が VULNERABLE） |
| 2 | 判定不能（判定行に達する前に失敗した、または判定行が無い） |

- 判定不能は結果ではない。評価エラーや試験の不備を直して再実行する
- 「防御は有効」と報告する前に、その試験が失敗し得ることを確かめる。常に成功する試験は何も示さない
- ノードには仮説に関わる設定だけを写す。実ホストの設定をそのまま import すると、LUKS や実デバイスへの依存で起動しない。写した値が実ホストと一致することは、雛形の `hostConfig`（実ホストの評価済み設定）との比較で担保する
- 試験ファイルは変更せずに再利用できる形に保つ。対策を当てた後も同じ試験で合否を確かめるためである

## 置き場所と評価の仕組み

- 試験は `~/Projects/nix-config/.defense-tests/<対象>-<短縮名>.nix`、ログは同ディレクトリの `logs/` に置く。このディレクトリは gitignore 済みで、コミットしない
- gitignore されたファイルは flake から見えないため、試験は flake の外から `builtins.getFlake` で nix-config を参照し、`nix build --impure -f` で実行する。nixpkgs は対象ホストのものを用いるため、flake.lock の固定に従う
- 置き場所は環境変数 `NIX_CONFIG_DIR` / `DEFENSE_TESTS_DIR` で変更できる

## 対策の差分を確かめる

対策を当てた状態は、本物のツリーではなく複製で評価する。

1. `run.sh sandbox <出力先>` で nix-config の複製（未コミットの変更を含む）を作る
2. `git -C <出力先> apply <差分>` で差分を当てる
3. `run.sh run --flake path:<出力先> <試験ファイル>` を、試験を変更せずに実行する

差分を当てる前に終了コード 1、当てた後に 0 となった場合のみ「塞がった」と言える。

## VM で確かめられないもの

- 顔認識そのもの（IR カメラ、認識率）。確かめられるのは PAM スタックの並びとフォールバックの挙動までである
- 実機の TPM の中身と PCR の実値。TPM の挙動は `virtualisation.tpm.enable = true`（swtpm）で再現できるが、実機の値は実機で読む
- tailnet lock の状態。実機で `tailscale lock status` を読む
- NixOS でない `arch-server` の設定

これらを報告する際は、VM で確かめた範囲と確かめていない範囲を分けて書く。

## 一連の流れの中での位置づけ

仮説の洗い出しから対策までを通す場合は、次の順に委譲する。本スキルは 2 と 5 の実行手段である。

1. `defense-recon` が現状を棚卸しし、仮説一覧を作る
2. `defense-validator` が仮説を 1 件ずつ確かめる
3. `defense-verifier` が「弱点が成立」の結果に反証をぶつける
4. `defense-patcher` が確定した弱点への差分を用意する（適用しない）
5. `defense-validator` が同じ試験で差分を確かめる

実環境への適用は、人間が差分を読んで承認してから行う。
