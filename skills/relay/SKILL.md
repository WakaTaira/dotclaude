# relay

設計が固まったあとの実装フェーズを自走させるためのスキルである。

このスキルが発動した時点で、**設計や方針はメインセッションですでに合意済みである**ことを前提とする。発動前にどこまで設計を詰めたかはユーザーの裁量であり、このスキルはその合意内容を所与として実装に着手する。設計自体をここでやり直してはならない。

## 役割分担

このスキルの核心は、レイヤーの分離にある。**relay のコアはメインセッションである。**

- **メインセッション = 設計・統括・監査レイヤー**
  全体設計の保持、タスク分解、サブエージェントへの指示、返ってきた成果物の監査を担う。原則としてメインセッションは実装の細部に直接手を下さない。grep 結果の羅列や試行錯誤のログでメインのコンテキストを汚さないことが、監査精度を保つうえで重要である。

- **サブエージェント（relay-*）= 実装・調査レイヤー**
  個別の作業を、それぞれ独立したコンテキストウィンドウで遂行する。

- **Codex 直接呼び出し = 外部の実装レイヤー**
  実装タスクの既定レーンは、メインセッションが Codex CLI（`codex exec`）を直接実行してネイティブ GPT に実装させる形をとる。メインに戻るのは GPT の最終応答（数千字）だけであり、監査の出力を小さく保てば「メインを汚さない」原則は維持できる。中継用のサブエージェントを挟まない理由は後述「クロスベンダーレーン」節に記す。

## 実行手順

以下の 5 ステップを順に実行する。ステップを飛ばさないこと。

### Step 1: タスク分解表を作る

サブエージェントを 1 体でもスポーンする前に、必ずタスク分解表を作成し、メッセージとして出力する。フォーマットは以下に固定する。

| # | タスク | 依存 | エージェント | 完了条件 |
|---|---|---|---|---|
| 1 | （何をするか） | なし | relay-investigator | （機械的に判定できる条件） |
| 2 | （何をするか） | #1 | relay-implementer-std | （同上） |

- **依存**: 先行タスクの番号。依存のないタスク同士は並列実行の候補になる
- **エージェント**: 後述の振り分け表のいずれか。Codex 直接呼び出しは `codex luna/low` `codex luna/max` `codex sol/high` のようにモデルと effort を添えて書く
- **完了条件**: 「テスト X が通る」「ファイル Y に関数 Z が存在する」など、監査時に機械的に検証できる形で書く。「〜が改善される」のような曖昧な条件は不可

**分解の粒度は並列度を最大化する側に倒す。** 対象ファイル集合が交わらないタスクは、内容的に近くても 1 タスクに束ねず別タスクとして切り出し、並列スポーンを既定とする。束ねてよいのは、複数の変更が同一ファイル群に乗る場合（同一ファイルへの並列書き込みは禁止のため）と、変更同士に順序依存がある場合のみ。「関連する修正だからまとめる」は束ねる理由にならない——束ねるほど 1 エージェントのコンテキストが濁り、監査の切り分けも粗くなる。

この表が実行フェーズ全体の台帳になる。タスクの追加・分割が必要になったら表を更新してから動く。

### Step 2: エージェントを選び、プロンプトを作る

サブエージェントはゼロから設計しない。`~/.claude/agents/` に定義済みの relay-* から、次の振り分け表に従って選ぶ。ハーネス側のモデル・effort・ツール権限・報告フォーマットは各エージェント定義に固定されており、ハーネスが機械的に強制する。Codex 直接呼び出しの引数・規律も relay-codex の定義（「呼び出しレシピ」節）に固定されており、統括者はそれを転記して呼ぶ。

#### 振り分け表

| エージェント | model / effort | 用途 |
|---|---|---|
| relay-investigator | fable / high | コードベース・仕様・原因の調査。選択肢と推奨を返す（読み取り専用） |
| relay-reviewer | fable / high | 変更差分の品質・整合性・セキュリティ評価（読み取り専用）。relay-codex-reviewer 失敗時のフォールバック先 |
| relay-codex-reviewer | sonnet / medium（レビュー本体は GPT `gpt-6-astra`、effort high） | レビュータスクの既定レーン。GPT の指摘の実在性を検証して返す（読み取り専用） |
| relay-implementer | opus / high | 複数ファイルにまたがる変更、並行処理・境界条件の実装、複雑なデバッグ |
| relay-implementer-std | sonnet / medium | 既存パターンに沿ったコード生成、リファクタリング |
| codex（直接呼び出し） | GPT `gpt-5.6-luna`（effort は難度で low / max）、最高難度のみ `gpt-5.6-sol` high | 実装タスクの既定レーン。統括者が `codex exec` を直接実行し、確定済みの仕様をネイティブ GPT に流す。レシピは relay-codex 定義の「呼び出しレシピ」節 |
| relay-codex | sonnet / medium（実装本体は同上） | 同レーンのサブエージェント版。長時間タスクを非同期で複数流したいときに統括者が選ぶ。結果を独立検証して返す |
| relay-verifier | sonnet / medium | ビルド・テスト・lint の実行と結果の一次評価（修正はしない） |
| relay-mechanic | haiku / low | ファイル探索、単純置換、定型コードの生成（判断を含まない作業のみ） |

relay-investigator / relay-reviewer の fable はメインセッションのモデルに追従しない固定である。メインで何を選んでいても、調査・監査の解像度はこの固定が保つ。

言語レベルの規約・スタイルの問題は、レビューエージェントではなく lint / formatter で機械的に解決する（実行は relay-verifier の検証に含める）。ドメイン特化の知見が必要な場合は既存の汎用エージェント（docs-lookup、architect など）を補助的に併用してよいが、実装フェーズの主経路は relay-* とし、モデル選択の一貫性を崩さないこと。

#### クロスベンダーレーン（Codex 直接呼び出し / relay-codex / relay-codex-reviewer）

実装タスクの既定レーンは Codex 直接呼び出し、レビュータスクの既定レーンは relay-codex-reviewer である。本体を Codex CLI（`codex exec`）経由のネイティブ GPT（実装は `gpt-5.6-luna` / `gpt-5.6-sol`、レビューは `gpt-6-astra`）が担うことで、単一ベンダーのモデル群が揃って見逃す問題を拾う。

- **実装（Codex 直接呼び出し）**: プロンプト必須 4 項目が書き切れ、完了条件に実行可能な検証コマンドが含まれる実装タスクは、原則このレーンに流す。統括者は次の手順で `codex exec` を自分で実行する（`codex mcp-server` は Codex CLI 0.154.0 で削除されたため、MCP 経由では呼ばない）
  1. セッション最初の呼び出し前に `~/.claude/agents/relay-codex.md` を Read し、「呼び出しレシピ」節（プリフライト・引数表・developer-instructions・応答の扱い）に従う。定義の正はそこに一本化し、この SKILL には転記しない
  2. 難度は 3 段に振り分ける——relay-implementer-std 相当の標準タスクは `gpt-5.6-luna` の effort `"low"`、relay-implementer 相当の高難度タスクは `gpt-5.6-luna` の effort `"max"`、luna max でも足りない最高難度（並行処理・境界条件が絡む複数ファイル変更、複雑なデバッグの実装部分）のみ `gpt-5.6-sol` の effort `"high"`。基本は luna の 2 段で足りる想定であり、sol は例外的に上げる段である。`gpt-6-astra` は実装レーンでは使わない（コスト）。判断軸はタスクの大きさではなく裁量の有無である——複数ファイルにまたがっていても仕様が確定していればこのレーンへ、裁量・設計判断・複雑なデバッグが残っているタスクは relay-implementer 系（Claude）に割り当てる。relay-mechanic 相当の機械的作業（判断を含まない探索・置換・定型生成）は従来どおり relay-mechanic に流し、codex のクォータを消費しない
  3. 実行は Bash の `run_in_background: true` で行う（実測で 1 件 6〜23 分かかり、Bash の上限 10 分を超えうるため）。依存のない複数タスクは、バックグラウンド実行を 1 メッセージに並べて並列に走らせる。完了通知を待つ間に、先に終わったタスクの監査を進めてよい。完了前に最終応答ファイルを読んで結果を推測しない
  4. 手に入るのは GPT の最終応答（`-o` のファイル）とスレッド ID（イベント jsonl の `thread.started` 行）のみである。検証は Step 4 の監査で行い、その出力は小さく保つ（`git status --short`、`git diff --stat`、テストは要点のみ tail）。ビルド・テストの実行は relay-verifier に委ねてよい
  5. GPT の確認質問は、合意済み設計から一義に答えられるものだけ `codex exec resume` で 1 回答えて続行させる。設計判断を要する質問は Step 5 の停止点（自走モードでは BLOCKED(DESIGN)）として扱い、統括者が代行しない
  - 中継用サブエージェント（relay-codex）を既定にしない理由: 実測で、サブエージェント経由は 1 タスクあたり 2〜9 万字の検証出力をサブ側で吸収する一方、メインに戻る報告（1.6k〜2.9k 字）は GPT の最終応答（1.2k〜1.9k 字）と同程度であり、メインの節約にはならない。加えてサブエージェントは CLAUDE.md 階層を毎回読み込む（起動時約 2.3 万トークン）。監査は Step 4 が担い、直接呼び出しもバックグラウンド実行で非同期にできるため、中継者を挟む利点は小さい
- **レビュー（relay-codex-reviewer）**: `gpt-6-astra`（effort high）を用いる。レビューはサブエージェント経由を維持する——GPT のレビュー本文は実測 6k〜11k 字と大きく、Critical / Major の実在性検証（該当行の Read）まで含めるとメインに載る量が報告（4k 字前後）の倍以上になるためである。指名したモデルが現行プランで利用できない場合は呼び出しが「モデル未提供」の明示エラーで失敗する——これは異常ではなく、フォールバックを起動する正規のシグナルである
- **フォールバック**: クロスベンダーレーンが「失敗」（Codex CLI 未導入・未認証・モデル未提供・クォータ枯渇・レート制限・GPT 利用不可）を返した場合は、同じ仕様のまま Claude レーンへ振り直す。実装は難度に応じて relay-implementer / relay-implementer-std、レビューは relay-reviewer。フォールバックした事実と理由は完了報告に明記する。挙動起因の「失敗」（GPT 側が実行に入らなかった・報告の体裁が成立しない・差分が空のまま完了を主張した等）は環境失敗と区別し、同一仕様での再試行 1 回か Claude レーンへの振り直しを統括者が選ぶ。「モデル未提供」で一度失敗したモデルは同一セッション中は再プローブせず、以降は直接 Claude レーンへ振ってよい（クォータ・レート起因はタスクごとに再試行してよい）

#### レビューの 2 軸分離

仕様が文書化されているタスク（完了条件が明確、または grill-me の成果物・PRD がある場合）のレビューは、**仕様軸**と**規約軸**の 2 タスクに分け、レビューレーン（既定 relay-codex-reviewer、フォールバック時 relay-reviewer）を並列で 2 体スポーンする。軸はスポーン時のプロンプトで指定し、軸の定義とスメルベースラインは relay-reviewer 側に定義済みである（relay-codex-reviewer もそこを参照してレビュー依頼（prompt）に転記する——定義の正は relay-reviewer に一本化する）。監査では 2 つの報告を軸別のまま並記して扱う。規約は守れているが仕様と違うコードと、仕様どおりだが規約に反するコードが、別々に見えている状態を保つ——軸をまたいだ統合ランキングは、一方の指摘がもう一方を覆い隠す原因になるため行わない。

2 体は観点に加えて、前提とする文脈も分ける。仕様軸には合意済み設計を渡すが、**規約軸には合意済み設計・ブリーフ・タスク分解表・完了条件を渡さない**。渡すのは変更差分と対象ファイルの範囲のみである（プロンプトの組み方は後述「プロンプト必須項目」の例外に従う）。リポジトリに文書化された規約（CONTRIBUTING.md、コーディング規約等）は、エージェントが自身の Read / Grep で参照してよい。禁じるのはそのタスク固有の設計文脈であり、リポジトリ全体の恒常的な規約ではない。意図は、規約軸のレビュアーに「この差分は単体で読んで筋が通るか」を判定させることにある——設計を知らない読み手にとって不可解なコードは、設計を知っている読み手にとっても保守できない。

監査では、規約軸の指摘が「設計上は妥当」である可能性を統括者が判断する。規約軸のレビュアーは設計を知らないため、設計上の必然を規約違反として報告し得る——その裁定は統括者の責務である。ただし裁定は指摘ごとに行い、規約軸の報告全体を「設計を知らないから」と一括で割り引いてはならない。

軽微な変更のレビューは、軸指定なしのレビューレーン 1 体（総合レビュー）で足りる。

#### レビュアー裁定の優先（レビュアーは正義）

レビュー指摘への対応は、レビュアーがどのレーン（GPT / Claude）であっても「指摘どおり修正する」を既定とする。実装レーンの反論・抗弁は裁定材料にしない——クロスベンダー構成では実装側とレビュー側でモデルファミリーが異なることが常態であり、ベンダー間の見解相違を実装側との往復で解消しようとすると膠着する。修正タスクの再ディスパッチでは、指摘を確定事項としてプロンプト / spec に転記する（対応する規律は relay-codex のレシピ（spec 冒頭文）/ relay-implementer / relay-implementer-std に焼き込み済み）。

例外は 2 つのみで、いずれも裁定は統括者が行う:

1. 指摘が合意済み設計と真正面から矛盾する場合（前節の統括者裁定。裁定は指摘ごとに行う）
2. 指摘どおりの修正がタスク分解表の別の完了条件を壊す場合

例外を適用したときは、その指摘・裁定・理由を完了報告に必ず含める。relay-codex-reviewer が「検証で不一致」（該当行が実在しない・指摘内容が現物と食い違う）と注記した指摘は例外裁定を経ずに棄却してよいが、棄却した事実は完了報告に残す。

#### プロンプト必須項目

サブエージェントはメインの会話を見られない。スポーン時のプロンプトには、必ず以下の 4 項目をすべて明記する。1 項目でも欠けたままスポーンしてはならない。Codex 直接呼び出しの spec（`prompt`）も同じ 4 項目で組み立てる。

1. **目的**: このタスクが全体のどの部分を担うか（1〜2 文）
2. **対象**: 触ってよいファイル・ディレクトリの明示的なリスト。対象外への変更は禁止と書く
3. **制約**: 合意済み設計のうちこのタスクに関わる決定事項、コーディング規約、やってはいけないこと
4. **完了条件**: タスク分解表の完了条件をそのまま転記

**例外（規約軸のレビューのみ）**: 前述「レビューの 2 軸分離」のとおり、規約軸のレビューレーン（relay-codex-reviewer / relay-reviewer のいずれであっても）にはタスク固有の設計文脈を渡さない。4 項目の骨組みは維持したまま、内容を次のとおり置き換える。この例外は規約軸のレビューにのみ適用し、仕様軸のレビューを含む他のサブエージェントには適用しない。

1. **目的**: タスク固有の文脈を含まない汎用の文言に置き換える
2. **対象**: 変更差分の範囲。通常どおりそのまま渡す
3. **制約**: リポジトリ規約に関する事項のみ。合意済み設計の決定事項は渡さない
4. **完了条件**: タスク分解表の完了条件は転記せず、「規約軸のレビュー報告を返すこと」に置き換える

#### 構造化報告

報告フォーマットは各エージェント定義に焼き込み済みのため、プロンプトへの転記は不要である。すべての relay-* は次の構造で報告を返すよう定義されており、監査はこの構造との突き合わせで行う。

```
## 結果: 完了 / 部分完了 / 失敗
## 変更ファイル: （フルパスの一覧。調査・検証・レビューでは「なし」）
## 実行コマンドと結果: （検証に使ったコマンドと、その出力の要点）
## 判断したこと: （指示になかったが現場判断した点。なければ「なし」）
## 未解決・懸念: （なければ「なし」）
```

クロスベンダーレーンのサブエージェント（relay-codex / relay-codex-reviewer）はこの構造に「## GPT の主張」欄（diff・検証との食い違いの明記欄）が加わる。監査ではこの欄の食い違い記載も確認する。

Codex 直接呼び出しにはこの報告構造がない。返るのは GPT の最終応答のみであり、それをサブエージェント報告と同じ位置づけ（裏取り前の主張）として Step 4 のチェックリストにかける。

### Step 3: 実行する

- 依存のないタスクは 1 メッセージ内で複数の Agent 呼び出し（Codex 直接呼び出しなら複数の `codex exec` のバックグラウンド実行）を並べ、並列実行する
- 依存のあるタスクは、先行タスクの**監査が通ってから**着手する。報告受領だけでは着手しない
- 実装型サブエージェントが同一ファイル群を触る場合は並列にしない。直列化するか、タスク分割を見直す

### Step 4: 監査する

サブエージェントの報告（または Codex 直接呼び出しの最終応答）を受けるたびに、メインセッションで以下のチェックリストを実行する。全項目を通過するまで次のタスクに進まない。Codex 直接呼び出しでは中継者の独立検証がないため、2（完了条件の裏取り）を省略してはならない。

1. **実在確認**: 報告された変更ファイルが実在し、報告どおりの変更が入っているか（Read で該当箇所を確認。全文読みは不要）
2. **完了条件の裏取り**: タスク分解表の完了条件を、機械的事実（コマンド実行結果）で確認する。ビルド・テストが関わる場合は relay-verifier に実行させるか、メインで直接コマンドを叩く。**サブエージェントの「成功しました」報告を裏取りなしに信用しない**
3. **越境確認**: 「対象」外のファイルに変更が漏れていないか（git diff の対象一覧などで確認）
4. **現場判断の裁定**: 報告の「判断したこと」欄を確認し、合意済み設計と矛盾しないか裁定する。矛盾する場合は差し戻す

監査で不合格になったタスクは、不合格理由を明記して同じエージェントに差し戻す。**2 回差し戻しても通らない場合は、そのタスクの進め方自体に問題があるとみなし、作業を止めてユーザーに状況を報告する。**

### Step 5: 停止点で止める

ユーザーの確認やテストが必要なポイントに達したら、そこで止めてユーザーに戻す。どこで止めるかは発動前の設計の詰め具合に依存するが、少なくとも以下では必ず止まる。

- タスク分解表のすべてのタスクが監査を通過したとき（完了報告）
- 合意済み設計の範囲を超える判断が必要になったとき
- 同一タスクが 2 回差し戻しになったとき
- 破壊的操作（削除、履歴改変、外部公開）が必要になったとき

## 難度判定の指針

- 「簡単そう」と「実際に簡単」は異なる。コンテキストの理解や判断を要するタスクは、見た目が単純でも relay-mechanic ではなく relay-implementer-std 以上に割り当てる。純粋に機械的（判断を含まない）と確信できる場合にのみ relay-mechanic を使う
- 迷ったら 1 段上のエージェントに倒す。差し戻しのやり直しコストのほうが、モデル 1 段分の差より高くつく
- ハーネス側の effort（各エージェント定義の frontmatter）はスポーン時に上書きできない。Claude レーンの調整レバーは「どのエージェントに割り当てるか」、クロスベンダーレーンの調整レバーは「GPT 側 effort（`model_reasoning_effort`）の指名」である（前述「クロスベンダーレーン」節）。実装は luna low / luna max / sol high の 3 段、レビューは astra high 固定。sol の xhigh / max はユーザーの明示指名時のみ、ultra（自動タスク委譲）は使わない

## ネストについて

relay-* エージェントは原則として Agent ツールを持たないリーフ（最終実行単位）であり、並列化はメインセッションがファンアウトで束ねる。1 つのタスク内に「調査してから実装する」のような直列の内部工程がある場合は、タスク分解表で別タスクに切り出し、メインが順に束ねる。

唯一の例外は relay-investigator である。調査は「広く掃いて一つの頭で統合する」形の仕事であり、掃く部分を子に逃がすことで統合用のコンテキストを汚さずに済む。そのため読み取り専用の Explore エージェントへの探索委譲のみを許可している（規律はエージェント定義側に記載）。書き込みを伴う作業のネストは全面的に不可である。

## 自走モード（無人運転）

ユーザーが /goal と併用して発動したとき、または無人での連続実行を明示したときは、以下の規律を追加する。ユーザーの介入は RELAY-STATUS の宣言によって機械的に呼び出すものであり、走行中の成果を随時見てもらうことは想定しない。

### 台帳の永続化

Step 1 のタスク分解表は、会話への出力に加えて TaskCreate でハーネスの Task 台帳に登録する（1 タスク = 1 Task。依存関係は addBlockedBy で表現する）。会話中の表はコンテキスト圧縮で失われうるため、進行状態の正は Task 台帳とする。着手時に in_progress、監査通過時に completed へ更新する。

### 状態宣言

毎ターンの末尾に、次の 1 行を必ず出力する。Step 5 の停止点に達したときは、対応する種別の BLOCKED を宣言して止まる。

`RELAY-STATUS: RUNNING | DONE | BLOCKED(DESIGN | MANUAL-TEST | PERMISSION | STUCK)`

- **RUNNING**: 台帳に未完了タスクが残っており、続行できる
- **DONE**: 全タスクが監査を通過し、完了報告を出した
- **BLOCKED(DESIGN)**: 合意済み設計の範囲を超える判断が必要。再グリル対象の論点を報告に含める
- **BLOCKED(MANUAL-TEST)**: ユーザーの実機確認が必要。確認手順を報告に含める
- **BLOCKED(PERMISSION)**: 権限確認で停止した
- **BLOCKED(STUCK)**: 同一タスクが 2 回差し戻しになった

この行は /goal の評価器が終了判定に使う機械的シグナルである。BLOCKED を宣言すべき局面で RUNNING を続けてはならない。評価器の圧力から逃れるために設計判断を代行することは、停止より悪い失敗である。

### 呼び戻し

DONE / BLOCKED で停止するときは PushNotification で通知する。内容は種別と、ユーザーに求める行動の 1 行とする。

### 開始前チェック

走り出す前に、完了条件の検証に使うコマンド群（テスト・ビルド・lint）と `codex exec` / `codex exec resume`（Bash）が権限プロンプトなしで実行できるかを確認する。未許可のものがあれば開始前にまとめてユーザーに確認する。走行中の権限待ちは、無人運転では停止と同義である。

### 推奨 /goal 条件（定型）

```
/goal RELAY-STATUS: DONE または BLOCKED が宣言されている
```

成果物の正しさは goal 評価器ではなく監査（完了条件の機械的裏取り）が担保する。goal 条件に成果物の状態を書き込む必要はない。DONE は機械的な完了条件の充足を意味し、受け入れ（意図どおりの成果物か）の最終判断は DONE 後のユーザーに残る。

### ループバック

- BLOCKED(DESIGN) → 該当分岐のみ再グリル（ADR / CONTEXT.md 更新）→ 台帳更新 → /goal 再設定で再開
- BLOCKED(MANUAL-TEST) → ユーザーの確認結果を受けて台帳更新 → /goal 再設定で再開
- BLOCKED(STUCK) → タスクの進め方自体を見直し、分解し直すか、ユーザーの指示を仰ぐ

BLOCKED でも goal は達成扱いで自動クリアされるため、介入後の再開は /goal の張り直しを 1 サイクルの単位とする。
