# 作業依頼書フォーマット

brief-me が出力する設計書の形式である。各節の見出しと順序は固定とし、節の省略はしない（該当なしの節は「なし」と明記する）。文体はである調。

```markdown
# 作業依頼: <タイトル>

## 対象

<触ってよいファイル・ディレクトリの明示的なリスト>

## 現状

<事実のみを書く。問題の評価・意見を混ぜない>

## 問題

<現状の何が困るのか。この変更の動機>

## 変更内容

### 1. <変更点>

<番号付き小節で、実装者の裁量が残らない粒度まで書く>

## 制約

- <変更しないもの・やってはいけないこと・文体等の指定>
- 上記の変更内容以外の編集を行わない。文言の改善や整理を巻き込まない

## 完了条件

- <機械的に判定できる形で書く。例: `git diff` の変更が対象ファイルに収まっている / テスト X が通る / ファイル Y に関数 Z が存在する>

## 受け入れ条件

<gauntlet がテストコードに変換する入力。1 項目 = 1 テスト>

- Given: <前提> / When: <操作> / Then: <期待結果>
```

## 各節の書き方

- **対象と制約が境界を二重に守る**: 対象は「ここは触ってよい」、制約は「これはしてはならない」。両方から読んで同じ境界が見える状態にする
- **完了条件と受け入れ条件の分担**: 完了条件は変更の形の検証（diff の範囲・存在確認）、受け入れ条件は振る舞いの検証（操作と期待結果）。形だけ合って動かないコードは受け入れ条件が弾き、動くが余計なことをするコードは完了条件が弾く
- **受け入れ条件に画面の感じ・操作感は書かない**: 機械判定できない項目は「手動確認」として完了条件の側に「ユーザーの実機確認」と明記する
