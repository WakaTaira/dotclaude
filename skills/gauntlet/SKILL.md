# gauntlet

設計書の受け入れ条件を、実装より先に書く受け入れテストへ変換するスキルである。仕様の正しさの担保をレビュアーの判断から機械的な関門へ移し、実装がこの関門を走り抜けたことをもって「仕様どおり」とする。

## 方式

Gherkin ランナー（cucumber 系）は使わない。Given / When / Then の構造だけを借り、プロジェクトの既存テストフレームワークで書く。step definition の維持コストを払わない。

- **配置**: `tests/acceptance/`（プロジェクトに既存のテスト配置規約があればそれに従う）
- **対応**: 受け入れ条件 1 項目 = テスト 1 本。テスト名とコメントに Given / When / Then を 1:1 で写し、設計書と突き合わせ可能に保つ
- **フレームワーク既定**（プロジェクトに既存があればそちらを優先）: Python = pytest / JS・TS = vitest / Rust = cargo test / シェル・CLI = bats / ブラウザ E2E = @playwright/test（NixOS では nix 管理の PLAYWRIGHT_BROWSERS_PATH 前提。npm 側の playwright は nixpkgs の driver と同系列のバージョンにする）/ TUI = bats + tmux（send-keys / capture-pane）
- **書き手**: テストコードは relay の Codex 実装レーン（`gpt-5.6-luna`、難度により `gpt-5.6-sol`）に書かせる。このセッション（統括者）は仕様の転記・呼び出し・red の裏取りを担い、テストコードを自分では書かない

## 実行手順

### Step 1: 入力を読む

設計書の「受け入れ条件」節を読む。節が無い設計書の場合は、完了条件から Given / When / Then を起こしてユーザーに提示し、承認を得てから進む。

### Step 2: テストを Codex レーンに書かせる

`~/.claude/agents/relay-codex.md` の「呼び出しレシピ」節（プリフライト・引数・応答の扱い）に従い、mcp__codex__codex を直接呼ぶ。レシピからの差分は次の 3 点のみである。

- **model / effort**: 既定は `gpt-5.6-luna` の `"max"`。関門の品質が実装全体の上限を決めるため。既存の `tests/acceptance/` にパターンが確立していて項目を足すだけなら luna の `"low"`。テストハーネス自体を新設する（tmux 併用の TUI、ブラウザ E2E など）場合のみ `gpt-5.6-sol` の `"high"`
- **spec（prompt）**: 必須 4 項目を次のとおり埋める
  1. 目的: 設計書名と、「実装より先に走る受け入れテストであり、実装は未着手である」こと
  2. 対象: `tests/acceptance/`（配置規約が別なら実際の配置先）のみ。フレームワーク設定ファイルの追加が必要ならそれも列挙する。実装コード・既存テストへの変更は禁止と書く
  3. 制約: 本スキルの「方式」節（ランナー・配置・1 項目 1 テスト・Given / When / Then の 1:1 転記）と、受け入れ条件の全文
  4. 完了条件: 「受け入れ条件の全項目がテスト化されているか、機械判定不能として最終応答に列挙されている」「テストを実行し、実装前なので全件 red であることを実際の出力で示す」
- **developer-instructions**: レシピの実装者ブロックの代わりに、次のテスト作成者ブロックを渡す

```
あなたは受け入れテストの作成者である。以下を厳守せよ。
- 変更してよいのは受け入れテストの配置先（仕様の「対象」）のみ。実装コード・既存テストは変更しない
- 受け入れ条件 1 項目につきテスト 1 本。テスト名とコメントに Given / When / Then を 1:1 で写し、設計書と突き合わせ可能に保つ
- テストは実装の振る舞いを外側から検証する。実装の内部構造を先取りして決めつけない
- 人為的に通したり落としたりしない（skip / xfail / 常に失敗する assert の禁止）。落ちる理由が「実装が未着手だから」になるように書く
- 機械判定できない項目（画面の感じ・操作感など）は無理にテスト化せず、最終応答に「機械判定不能」として列挙する
- 書いたテストを実行し、その実際の出力を最終応答に含める。最終応答は簡潔にする。作成ファイルの一覧、実行コマンドと出力の要点、機械判定不能の項目、の 3 節のみ
```

GPT が「機械判定不能」とした項目は、統括者が妥当性を確認したうえで「手動確認」として設計書の完了条件へ差し戻す。全項目が「テスト化済み」か「手動確認へ差し戻し」のどちらかに割り当てられたら Step 2 は完了である。

Codex レーンが失敗（CLI 未導入・未認証・モデル未提供・クォータ枯渇・レート制限）を返した場合は、同じ spec と作成者ブロックを、難度に応じて relay-implementer / relay-implementer-std（Claude レーン）にサブエージェントとして振り直す。フォールバックした事実と理由は Step 4 の報告に含める。

### Step 3: red を確認する

GPT の最終応答に含まれる実行結果を鵜呑みにせず、テストコマンドを自分で再実行して落ちることを確認する（出力は要点のみ tail で保つ）。最初から通るテストは何も検証していない。通ってしまうテストがあれば、同じスレッドに mcp__codex__codex-reply で該当テスト名と「実装未着手で red になるよう書き直すこと」を 1 回だけ差し戻す。それでも直らなければ Claude レーンへ振り直す。既存挙動の変更等で red にできないテストがある場合は、その理由を報告に明記する。

### Step 4: relay へ渡す形で報告する

次の 2 行を含めて報告し、終了する。

- タスク分解表の完了条件に書く 1 行: 「`tests/acceptance/<file>` のテストが通る」
- 実装タスクの「対象」欄に書く 1 行: 「`tests/acceptance/` 配下への変更は禁止」（テストを書く者と実装する者を分離し、実装側がテストを都合よく書き換える経路を機械的に塞ぐ。書き手と実装者が同じモデルであっても、別スレッド・別 spec・対象の排他によって分離は保たれる）
