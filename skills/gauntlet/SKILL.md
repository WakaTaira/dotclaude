# gauntlet

設計書の受け入れ条件を、実装より先に書く受け入れテストへ変換するスキルである。仕様の正しさの担保をレビュアーの判断から機械的な関門へ移し、実装がこの関門を走り抜けたことをもって「仕様どおり」とする。

## 方式

Gherkin ランナー（cucumber 系）は使わない。Given / When / Then の構造だけを借り、プロジェクトの既存テストフレームワークで書く。step definition の維持コストを払わない。

- **配置**: `tests/acceptance/`（プロジェクトに既存のテスト配置規約があればそれに従う）
- **対応**: 受け入れ条件 1 項目 = テスト 1 本。テスト名とコメントに Given / When / Then を 1:1 で写し、設計書と突き合わせ可能に保つ
- **フレームワーク既定**（プロジェクトに既存があればそちらを優先）: Python = pytest / JS・TS = vitest / Rust = cargo test / シェル・CLI = bats / ブラウザ E2E = @playwright/test（NixOS では nix 管理の PLAYWRIGHT_BROWSERS_PATH 前提。npm 側の playwright は nixpkgs の driver と同系列のバージョンにする）/ TUI = bats + tmux（send-keys / capture-pane）

## 実行手順

### Step 1: 入力を読む

設計書の「受け入れ条件」節を読む。節が無い設計書の場合は、完了条件から Given / When / Then を起こしてユーザーに提示し、承認を得てから進む。

### Step 2: テストを書く

受け入れ条件の全項目がテストになるまで書く。機械判定できない項目（画面の感じ・操作感）は無理にテスト化せず、「手動確認」として設計書の完了条件へ差し戻す。全項目が「テスト化済み」か「手動確認へ差し戻し」のどちらかに割り当てられたら完了である。

### Step 3: red を確認する

書いたテストを実行し、実装前なので落ちることを確認する（red）。最初から通るテストは何も検証していない。既存挙動の変更等で red にできないテストがある場合は、その理由を報告に明記する。

### Step 4: relay へ渡す形で報告する

次の 2 行を含めて報告し、終了する。

- タスク分解表の完了条件に書く 1 行: 「`tests/acceptance/<file>` のテストが通る」
- 実装タスクの「対象」欄に書く 1 行: 「`tests/acceptance/` 配下への変更は禁止」（テストを書く者と実装する者を分離し、実装側がテストを都合よく書き換える経路を機械的に塞ぐ）
